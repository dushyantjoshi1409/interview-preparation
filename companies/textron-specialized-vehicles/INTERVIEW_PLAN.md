## 7. Technical Question Bank With Model Answers and Analogies

### A. Productionizing an AI model

**Question:** How would you take a data scientist's model into production?

> First, I would define a clear contract: input schema, output schema, model version, confidence signal, latency target, and known limitations. I would package the model behind a versioned API, validate inputs, add authentication and authorization, timeouts, retries, and a safe fallback. I would test the model and the application separately, then run an end-to-end evaluation on representative cases. I would deploy gradually, monitor quality, latency, errors, cost, and drift, and keep a rollback path. I would also record user feedback without storing unnecessary sensitive data.

**Analogy:** A model is an engine. Productionizing it means building the full car: controls, brakes, dashboard, seat belts, maintenance plan, and driver instructions.

### B. RAG design

**Question:** Explain RAG in simple terms.

> RAG retrieves relevant company information before asking the model to answer. A typical flow is document ingestion, cleaning, chunking, embeddings, indexing, retrieval, optional reranking, prompt construction, generation, citations, and evaluation. It improves freshness and grounding, but it does not automatically guarantee truth. Poor retrieval can still produce a confident wrong answer.

**Analogy:** It is an open-book exam. The model still reasons, but it receives the most relevant pages before answering.

**Question:** How would you improve a weak RAG system?

> I would separate retrieval failure from generation failure. For retrieval, I would test chunking, metadata, hybrid search, filters, top-k, reranking, and query rewriting. For generation, I would improve instructions, require citations, tell the model to abstain when evidence is missing, and reduce irrelevant context. I would evaluate on a labeled question set with retrieval recall, faithfulness, answer relevance, latency, and cost.

### C. Confidence thresholds and human handoff

**Question:** How do you calculate confidence for an LLM answer?

> I would not trust one number from the model. I would combine signals such as retrieval relevance, reranker score, whether the answer is supported by cited text, tool success, rule checks, model agreement or evaluator score, and the risk of the use case. I would calibrate thresholds on historical labeled cases. High-confidence cases can be answered automatically, medium-confidence cases can ask a clarifying question or show a warning, and low-confidence or high-risk cases should go to a human.

**Analogy:** Airport security does not make every passenger follow the same path. It uses multiple signals, and uncertain or high-risk cases receive a manual check.

**Question:** Design escalation logic.

> I would define explicit states such as answered, needs-clarification, handed-off, and failed. The handoff packet should include the user's question, retrieved sources, attempted actions, confidence signals, and a short summary, while excluding sensitive information the human does not need. I would prevent loops, set a timeout, show the user what is happening, and measure handoff rate, resolution time, re-open rate, and false escalation rate.

### H. Testing AI applications

**Question:** How do you test a non-deterministic AI system?

> I use several layers. Unit tests cover deterministic code such as parsing, routing rules, and access checks. Contract tests cover model and enterprise APIs. Retrieval tests measure whether the right evidence appears. Evaluation tests use a versioned dataset for faithfulness, relevance, safety, and refusal behavior. End-to-end tests cover the user flow, including handoff. Load tests cover latency and rate limits. Before release, I compare the new prompt or model against the current version and use a gradual rollout with rollback.

**Analogy:** You cannot test a self-driving feature with only one perfect road. You need normal roads, rain, missing signs, unsafe situations, and a safe fallback.

### I. APIs and microservices

**Question:** What makes an AI API production-ready?

> A clear versioned schema, authentication, authorization, validation, bounded timeouts, retry rules, idempotency, rate limits, structured errors, correlation IDs, tracing, health checks, and backward compatibility. For long AI tasks, I would consider an asynchronous job with status polling or events instead of keeping one HTTP request open.

**Question:** When would you use microservices?

> I use a separate service when it has a clear business boundary, independent scaling or security needs, or a different release lifecycle. I would not split a small application just because microservices sound modern. A modular monolith is often simpler until the boundaries are proven.

### J. SQL and data

**Question:** How do you prevent an AI agent from running unsafe SQL?

> Use a read-only account, allowlisted schemas or approved query templates, row-level security, query parsing, limits on rows and execution time, blocked write statements, audit logs, and confirmation for sensitive operations. In high-risk cases, the model should select an approved tool rather than write arbitrary SQL.

**Question:** SQL versus vector search?

> SQL is best for exact structured facts, filters, joins, and aggregation. Vector search is useful for semantic similarity in text or other unstructured content. Hybrid applications often use both: SQL for "how many orders failed last week" and RAG for "what does the service policy say about this failure?"

### K. Frontend and user experience

**Question:** What should an enterprise AI chat UI show?

> It should show the answer, sources, freshness, important uncertainty, what action will happen before it happens, and a clear way to correct or escalate. It should preserve conversation state carefully, meet accessibility requirements, handle slow responses and errors, and never make the user guess whether a write action succeeded.

**Analogy:** A good dashboard is not only a steering wheel. It also has warning lights, mirrors, and clear confirmation when the car changes direction.

### Coding question 1 - Route by confidence and risk

**Prompt:** Given retrieval, groundedness, and policy scores between 0 and 1, decide whether to answer, ask for clarification, or hand off. High-risk requests must always go to a human.

```python
def route_request(
    retrieval_score: float,
    groundedness_score: float,
    policy_score: float,
    high_risk: bool,
) -> str:
    scores = (retrieval_score, groundedness_score, policy_score)
    if any(score < 0 or score > 1 for score in scores):
        raise ValueError("scores must be between 0 and 1")

    if high_risk or policy_score < 0.80:
        return "human_handoff"
    if retrieval_score < 0.60 or groundedness_score < 0.70:
        return "ask_clarifying_question"
    return "answer"
```

**Easy explanation:** Validate the data first. Safety overrides confidence. Weak evidence asks for more information instead of guessing. In production, thresholds must be calibrated on labeled business cases, not chosen casually.

**Complexity:** Time O(1), space O(1).

### Coding question 2 - Keep the latest event per request

**Prompt:** Given events containing `request_id`, `timestamp`, and `status`, return the latest status for each request.

```python
def latest_status(events: list[dict]) -> dict[str, str]:
    latest: dict[str, tuple[int, str]] = {}

    for event in events:
        request_id = event["request_id"]
        timestamp = event["timestamp"]
        status = event["status"]

        if request_id not in latest or timestamp > latest[request_id][0]:
            latest[request_id] = (timestamp, status)

    return {
        request_id: timestamp_and_status[1]
        for request_id, timestamp_and_status in latest.items()
    }
```

**Easy explanation:** Use a dictionary like one labeled box per request. Replace the value only when the new event is newer.

**Complexity:** Time O(n), space O(k), where k is the number of unique requests.

### Coding question 3 - Top failed intents

**Prompt:** Return the `k` most common failed user intents from a list.

```python
from collections import Counter


def top_failed_intents(failed_intents: list[str], k: int) -> list[tuple[str, int]]:
    if k <= 0:
        return []
    return Counter(failed_intents).most_common(k)
```

**Easy explanation:** Count each intent and return the largest counts. This could help prioritize prompts, knowledge, or workflows that need improvement.

**Complexity:** Counting is O(n). Selecting the top k is commonly O(m log k), where m is the number of unique intents. Space is O(m).

### Coding question 4 - SQL for low-confidence monitoring

**Prompt:** Find users who had at least three low-confidence responses in the last seven days.

```sql
SELECT
    user_id,
    COUNT(*) AS low_confidence_count
FROM ai_responses
WHERE created_at >= CURRENT_TIMESTAMP - INTERVAL '7 days'
  AND confidence_score < 0.60
GROUP BY user_id
HAVING COUNT(*) >= 3
ORDER BY low_confidence_count DESC;
```

**Easy explanation:** Filter the time and confidence first, group by user, then keep only groups with three or more events. Mention that date syntax differs by database.

**Performance note:** Consider an index starting with `created_at`, and review whether `user_id` and `confidence_score` should be included based on the database and query plan.

### Coding question 5 - Basic fallback: first non-repeating character

**Prompt:** Return the first character that appears only once.

```python
from collections import Counter


def first_unique_character(text: str) -> str | None:
    counts = Counter(text)
    for character in text:
        if counts[character] == 1:
            return character
    return None
```

**Easy explanation:** First count everything, then scan in original order so "first" is preserved.

**Complexity:** Time O(n), space O(k), where k is the number of distinct characters.
